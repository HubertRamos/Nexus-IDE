1.6 Conversao posicao/texto: caracter vs byte vs UTF-16
-------------------------------------------------------
[FATO] Cargo: Rope e String sao UTF-8. A nexus Workcomo "char offsets"
      (escalares Unicode), sempre.
[FATO] tree-sitter usa offsets de byte (Point { row, col }) e InputEdit com
      start_byte, old_end_byte, new_end_byte (bytes), nao caracteres.
[FATO] Nexus ja possui o conversor que precisa entre os dois para sintaxe:
      LineIndex::char_to_byte, byte_to_char, point(byte) -> tree_sitter
      Point   [state.rs:460-548]
[FATO] O LSP exige posicoes no formato UTF-16: Position { line: u32,
      character: u32 } onde "character" e o offset em UNIDADES UTF-16.
[FATO] Em Rust, char.len_utf16() pode ser 1 (quase todos os caracteres
      comuns) ou 2 (caracteres do plano multigoal: emoji, caracteres
      historicos, etc.).
[CONCLUSAO] A conversao UTF-16 precisa ser implementada externamente ao
      core (em nexus-lsp), pois o core nao possui funcoes UTF-16.

3. BIBLIOTECAS RUST RECOMENDADAS (sem adicionar deps nesta etapa)
================================================================================

3.1 Comparacao de alternativas para JSON-RPC 2.0
------------------------------------------------
[Compara] jsonrpc-derive + serde: geracao de codigo para serializacao de
      req/resp. Pros: produtividade, tipos seguros. Contras: sincrono no
      nucleo, tempo de compilacao maior, depende de derive macros.
      [RECOMENDACAO] possivel em etapas posteriores, se fuer preferido.

[Compara] jsonrpc-core (+ client): biblioteca sincrona madura, baixo
      nivel. Pros: estabilidade, controle total. Contras: nao tem
      transporte stdin/e processo; voce mesmo precisa implementar
      canal, timeouts e mapeamento de ids.

[Compara] jsonrpc-rs (jsonrpc-core-server, jsonrpc-core-client,
      jsonrpc-process): ja inclui transporte de STDIO e gerenciamento
      de processos. Pros: focado em JSON-RPC over STDIO. Contras:
      ecossistema menor, documentacao mais antiga, dependencias mais
      pesadas.

[Compara] lsp-types: definicoes tipadas do protocolo LSP. Pros: mao
      de payloads validos; constante do.ecossistema. Contras: so
      tipos; nao resolve comunicacao.

[Compara] Tokio (rt, io-util, sync): runtime assincrono maduro,
      suporta Linux e Windows. Pros: IO assincrona nativa; facil
      de testar com fake servers. Contras: precisa implementar
      a camada de mensageria JSON-RPC (instancia de codigo).

[Compara] serde_json + async-channel + manual: implementacao
      minimalista de JSON-RPC 2.0 sobre STDIO (linhas de texto).
      Pros: controle total, dependencias minimas, facil debug e
      teste. Contras: voce implementa map de ids, timeouts,
      batching.

[RECOMENDACAO PRATICA PARA ETAPA 1]
- Usar serde_json + tokio (rt, io-util, sync, net) + implementacao
  manual de JSON-RPC 2.0 sobre STDIO (linha a linha).
- Motivos: menor ligacao, sem dependencias externas de protocolo
  (jsonrpc-rs, jsonrpc-derive), teste simples com servidor fake,
  robustez de erros explicitos.
- Depois valer a pena analisar se vale a pena trocar por
  jsonrpc-derive ou lsp-types (tipos) para etapas futuras.

3.2 Dependencias propostas para Etapa 1 (apesar de instrucao de nao
    adicionar, apresentacao para decisao futura)
[PROPOSED] tokio (rt, io-util, sync, net)
[PROPOSED] serde_json

4. CONVERSAO CORRETA ENTRE POSICOES INTERNA E UTF-16
================================================================================

4.1 Regras empiricas
--------------------
[FATO] Nexus: offsets no domain de caracteres Unicode (escalar).
[FATO] LSP: Position { line, character }, character = UTF-16 code unit.
[FATO] Rust str: UTF-8; char.len_utf16() = 1 para a maioria dos
      caracteres, = 2 para caracteres do plano multigoal (emoji,
      histricos, etc.).
[FATO] Nao existem "lone surrogates" em str valido (Rust garante que
      o texto e UTF-8 valido).

4.2 Metodo proposto (implementar em nexus-lsp/src/position.rs)
-------------------------------------------------------------
- char_offset_to_utf16(text, CharOffset): percorre chars ate o offset,
  somando char.len_utf16() de cada char.
- utf16_offset_to_char(text, u32): avanca por chars, acumulando unidades
  UTF-16 ate alcançar o alvo; retorna CharOffset.
- char_len_to_utf16(len_chars): ultrapassando para um documento.
- position_from_line_character(text, line, u32 character): usa
  line_of_char + conversao dentro da linha.
- location_to_position / position_to_location: opera sobre o texto do
  documento.

4.3 Cuidados especiais
----------------------
[PROCEDimento] Certifique-se de que os testes cobrem:
- ASCII (todos 1 unidade).
- "café" (e com acento, 1 unidade).
- "界" (CJK, 1 unidade, mas largura dupla na UI).
- "😀" ou qualquer emoji (2 unidades UTF-16).
- offset no final do documento (offset == len_chars).
- CRLF: trate \r\n como um unico fim de linha, e nao conte \r como
  caracter separado na conversao.
- Linhas vazias e caracteres de tabuacao.

4.4 Envio de texto
------------------
[PROCEDUTO] O texto do documento e enviado como JSON UTF-8 (os codepoints
      mapeiam 1:1). A conversao UTF-16 e obrigatoria apenas para
      Position (character). Em etapas futuras, e possivel suportar
      textDocument/positionEncoding para servidores que querem codigos
      explcitos UTF-16.

5. SINCRONIZACAO DE DOCUMENTOS E CONTROLE DE VERSOES

5.1 Identidade de documento
---------------------------
[FATO] Document path eh canonizado em open/save/set_path.
      (canonicalize em open_document, save_document_to, set_path).
[RECOMENDACAO] A URI do documento para LSP = conversion de path para

      para uri eh obrigatorio).
[RECOMENDACAO] Em Etapa 1, use um identificador interno (path absoluto
      canonizado) como chave de documento no registry do LSP.

5.2 Versao do documento
-----------------------
[FATO] Buffer::revision() NÃO e monotonico: undo() volta para
      revision_before. [FATO, buffer/mod.rs:484-485]
[RECOMENDACAO] Manter um contador independente "version" (u64)
      por documento, incrementado em todo envio (didOpen=1,
      didChange=version+1, etc.), armazenado no LspWorkspace/client,
      nao no buffer.
[RECOMENDACAO] Nao usar Buffer::revision como LSP version.

5.3 Estrategia de sincronizacao
-------------------------------
[STACK] (a) textDocument/didOpen: na abertura do arquivo (version=1).
      (b) textDocument/didChange: a cada edicao confirmada (version++
          e TextDocumentContentChangeEvent range/rangeLength/text).
      (c) textDocument/didSave: no save() (apenas se server suportar).
      (d) textDocument/didClose: na conclusao do documento.
[PROCEDIMO] Envio ativo apos commit_session; nao aguardar resposta
      antes de continuar a interface.
[PROCEDIMO] Full sync opicional: em seguida de reload ou se o servidor
      pedir reenvio, reenviar o texto completo.

5.4 Conflitos e modificacao externa
------------------------------------
[FATO] App expoe has_conflict() e recovered flags.
[FATO] watcher::detect_change compara fingerprint (len+hash) do disco.
[NOTA] A LSP nao eh notificada automaticamente de alteracoes externas.
      O cliente decide: apenas enviar do usuario; opcionalmente
      "reload" para o servidor quando o usuario usar Ctrl+R.
[RECOMENDACAO] Em Etapa 1, nao enviar didChange em conflito;
      aguardar explicitamente a decisao do usuario.

6. CICLO DE VIDA DOS SERVEORES DE LINGUAGEM
================================================================================

[RECOMENDACAO] Sempre iniciar servidores externos via spawn com STDIO:
- stdout pipe (JSON-RPC).
- stderr pipe (log do servidor, nao saida do protocolo).
- stdin pipe (escrita de requisicoes/notificacoes).
- aguardar handshake: getProcessId, enviar initialize e aguardar resposta.

[ESTAGIO] Inicializacao (handshake)
- send initialize com capabilities do cliente (completion, hover,
  goto_definition, references, rename, code_action, formatting,
  publication_diagnostics etc.), trace = "off", etc.
- aguardar response "initialize".
- enviar initialized (notificacao).
- registrar todas as outras opcoes com registerCapability, se suportado.

[ESTAGIO] Em funcao
- manter um "lobby" de processos: um Server por linguagem/projeto.
- aguardar death do processo (poll/wait) para tratar falhas.
- quando o processo morrer: notificar App, registrar stderr capturado,
  marcar documento "server died", opcionalmente reiniciar (flag
  restart_on_crash).

[ENCERRAMENTO] graceful shutdown
- enviar shutdown, aguardar resposta, depois exit (notificao).
- apos shutdown, matar o processo (kill), aguardar (wait) para evitar
  zombies; no Unix, usar setpgid + matar o grupo (depois de testado).
- no Windows, usar TerminateProcess + WaitForSingleObject.

[SEM ORFAS] Nenhum processo deve escapar.
- todos os pipes sao fechados no processo filho.
- use std::process::Command::spawn + pipes; nao use shell
  buzinas para evitar interpretao de caracteres.
- em caso de colheita, matar e aguardar.

[SEPARA CAO DE LOG] stderr do servidor nunca deve misturar com o
      stdout da aplicacao; use buffer circular ou arquivos.

[VALIDACAO] Mensagens recebidas:
- json parse falho: descartar, log.
- metodo desconhecido: log, ignorar.
- response com id diferente da req atual: ignorar (resposta antiga).
- timeout: descartar requisição e avisar.

7. INTEGRAÇAO COM DOCUMENTMANAGER SEM BLOQUEAR A TUI
================================================================================

[RECOMENDACAO] Nao modificar DocumentManager. A adicao do LSP deve ficar
      na camada App (nexus-tui) + crate nexus-lsp.

[Estrutura] App retem:
- lsp_workspaces: HashMap<workspace_path, LspWorkspace>
- LspWorkspace mantém: clients: HashMap<document_uri, LspClient>,
  version counters, capability registry.

[Ciclo de vida por documento]
- open_document: registrar documento no LspWorkspace; decidir cliente
  (por LanguageId); chamar client.start() se for o primeiro doc dessa
  linguagem.
- close_document: remover do registry; se sobrou cliente, mantê-lo;
  se nao houver mais docs, destroi o cliente.
- open_workspace: registrar o workspace e o hub de servidores.
- switch_tab: invisibilidade do documento inativo; manter cliente vivo
  (o servidor so pode estar sem o buffer, mas o client fica ativo).
- save_document_to: chamar client.did_save().
- restore_session: recriar hierarchy a partir do path de cada
  Document.

[Envio de edicao]
- Apos commit_session (transacao do buffer concluida), chamar
  lsp_notify_did_change(doc, version, text) do cliente.
- Nao depender da View/Settings; usar Document::buffer e Document::path.

[Threading]
- Toda a comunicacao com o servidor fica em worker pool (Tokio) ou
  thread do lado do cliente. O loop da TUI permanece dedicado a:
  - poll (250ms) [event.rs:12]
  - render com ratatui (terminal::Terminal)
  - input (crossterm)
- Nenhum método do DocumentManager roda no event loop; o bridge chama
  methods do LspClient (que agem sobre canais/async).

[Isolamento]
- O buffer nunca é alterado por JSON-RPC do servidor: edicoes sao
  feitas apenas via Buffer::apply_edit (que retorna Result).
- Diagnosticos, hover e completacao vem do servidor para o store de
  UI; a UI renderiza conforme vacilabilidade e focus de documento.

9. RISCOS TECNICO E DECISAO ARQUITETURAL
================================================================================

[Risco] Event loop bloqueado por IO com servidor
[Impacto] Alta (TUI congelada)
[Medida] I/O com servidor so em worker/async; nao chamar blocks no loop.

[Risco] Conversao UTF-16 incorreta
[Impacto] Alta (posicao invalida, cursor off)
[Medida] Unidades de teste abrangentes (seção 4.3); code review commit
         audit para shifts/surrogates.

[Risco] Server morre inesperadamente
[Impacto] Medio (doc nao e sincronizado)
[Medida] Monitor process; notificar App; stderr isolado; opcao
         restart_on_crash=false default.

[Risco] Resposta antiga sobrescreve a recente
[Impacto] Alto (UI mostra dados velhos)
[Medida] ID + sequence + timeout + invalidate on new request.

[Risco] Panic no servidor
[Impacto] Medio
[Medida] stderr isolado; error reportada; nao propagar exception para
         App.

[Risco] STDOUT server nao e JSON-RPC
[Impacto] Alto (protocolo quebrado)
[Medida] Parse linha a linha; descartar e terminar o server.

[Risco] Processo-orphan no Windows/Unix
[Impacto] Alto
[Medida] wait() apos kill; matar grupo no Unix (setpgid); testar no CI.

[Risco] Buffer corrompido pelo servidor
[Impacto] Baixo
[Medida] Edicoes so via Buffer::apply_edit; RecoveryPending bloqueia UI.

[Risco] Config global misturada com server
[Impacto] Medio
[Medida] Config de servidores em bloco proprio; nao na ThemeConfig.

[Risco] Linguagem nao suportada
[Impacto] Baixo
[Medida] Fallback a texto simples; nao iniciar server para idioma
         desconhecido.

[Risco] A integridade da 1.4 e perdida
[Impacto] Critico
[Medida] Registro de cliente na App external; nao alterar
         DocumentManager; tests de regressao 360 testes.
